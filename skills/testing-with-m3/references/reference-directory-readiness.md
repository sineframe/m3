# Directory readiness

`m3 lint --directory` checks an MCP server's metadata against the published
listing rules of three directories:

- `claude`: the Claude connector directory;
- `openai`: the OpenAI plugin directory, which ChatGPT and Codex share;
- `muse`: the Muse connector directory (Meta).

```sh
m3 lint https://example.com/mcp --directory all
m3 lint --directory claude --directory openai -- python server.py
m3 lint --directory claude --harness claude_code -- python server.py
```

`--directory` is repeatable and `all` picks the three. With directories alone,
only directory checks run; add `--harness` to run the Claude Code and Codex
checks as well. Without `--directory`, `m3 lint` behaves exactly as before.
Like every lint check, directory checks only read what the server lists: they
never call a tool, never contact a model and never print header values.
With directories alone, a `tools/list` that fails, or that has entries which
are not tools with a string name, exits with status 2: nothing could be
checked. Run without `--directory` to see what is wrong with the listing.

**Passing does not mean a directory will approve the server.** Reviewers also
test behaviour, authentication, privacy policies, documentation and use
cases, none of which metadata shows. These checks catch the listing rules that
the metadata can show, before a reviewer does. For the checks that need
judgment, install the
[preparing-directory-submissions agent skill](https://m3.sineframe.com/docs/guides/agents/skill#prepare-a-directory-submission):
your coding agent runs these lint checks, then reads the code, docs and
listing, and writes one readiness report.

## Reading a finding

```
ERROR   directory-claude-safety-hints  tool 'create_issue' annotations
  detail: readOnlyHint absent, destructiveHint absent
  claude [error]: missing the applicable safety hint. https://claude.com/docs/connectors/building/review-criteria#provide-tool-annotations (policy checked 2026-10-18)
  fix: Set "readOnlyHint": true if this tool only reads; otherwise set "destructiveHint" (true if it modifies or deletes data). Claude's MCP page asks for both hints on every tool.
```

Each finding names the rule and the field, the observed fact, one line per
chosen directory with its severity and the policy section it comes from, and
a fix. The JSON report carries the same per directory under `directories`,
including the verbatim policy `quote` and `policy_date`. The last line of the
human report counts findings per directory. If `tools/list` failed or stopped
early, that line starts with `directory readiness: incomplete` and covers only
the tools that were read.

- **error**: the policy states a requirement or a rejection reason, and every
  tool matching the condition breaks it, whatever the tool does. Errors fail
  the run under the default `--fail-on error`.
- **warning**: the policy rule is real, but the condition only suggests a
  breach (for example, a method input that lists both GET and POST, or
  invisible characters that may hide text). The summary says "may", and the
  fix says what to check first. Warnings fail the run only with
  `--fail-on warning`.

## Policy versions

The rules were checked against each directory's published pages on
**2026-10-18**, and every report shows that date. Directories change their
rules; when they do, the quotes and the date are updated together.
`python3 benchmarks/lint-oracle/oracle.py --policies` checks every quote
against its live section.

## Not checked

- **Anything that depends on what text means.** This covers steering
  language in descriptions or server instructions (preferring this tool,
  avoiding other tools or web search, asking for calls on every turn,
  overriding instructions), unsupported use cases (moving money, placing
  trades, generating media with AI), tool names that contradict their hints,
  free-form API tools that don't name their API, and inputs that ask for
  credentials, payment data, government IDs, precise location or conversation
  history. Patterns can't decide these correctly; they need judgment.
- **Muse.** Muse classifies tools from your documentation rather than MCP
  annotations, and its listing rules are about meaning, so no rule checks
  Muse from metadata yet. `--directory muse` reports it as not checked, never
  as passing.
- **Listing names**, such as OpenAI's rule against appending "MCP" or
  "Plugin" to a product name: the listing name isn't in the server's
  metadata.
- **Empty tool names:** no directory addresses them (the Claude Code and
  Codex checks still do).
- **Anything that needs calling a tool:** response size, error messages,
  authentication, and whether descriptions match behaviour.
