01 — What it actually is

Four products wearing one repository

"MCP Inspector" undersells it. MCPJam ships a debugger, a CLI, an SDK, and a hosted SaaS, plus Slack and Discord bots, a Cloudflare Worker that is itself an MCP server, and a widget renderer for ChatGPT Apps.

The four surfaces

Inspector
A local web app (npx, port 6274), an Electron desktop app, or the hosted cloud version. Connect, poke, watch traffic.
CLI
@mcpjam/cli — 27 command modules. Inspection, conformance, OAuth, evals, tunnels, projects. Built for CI.
SDK
@mcpjam/sdk — the reusable core: client manager, eval framework, OAuth, conformance suites. 201k lines.
Hosted
app.mcpjam.com — accounts, orgs, projects, shared results, metered LLM credits, scheduled evals, GitHub PR checks.

MCPJam is not winning on distribution — it is winning on depth, and betting that depth converts to a hosted subscription. licenceLICENSE · mcpjam-inspector/server/evals/LICENSE

It is open-core, and the split is not where you would guess

Apache 2.0 for the app, SDK and CLI — except everything under server/services/ and server/routes/mcp/evals.ts, which fall under a separate "MCPJam Enterprise Edition" licence: source-available, free for development and testing, paid subscription required for production use, modifications assigned back to MCPJam.

That carve-out is not a corner of the codebase. server/services/ is where evals-runner.ts, the RPC log bus, the tunnel manager, the connection worker and the GitHub checks worker all live. Entitlement language is pervasive: subscription appears in 158 files, billing in 213, isPro in 52. If you are rebuilding, you cannot lift that directory — you must reimplement it.

The database is a hole in the diagram

Every durable write goes out as fetch(${CONVEX_HTTP_URL}${path}) with a single static x-inspector-service-token header. There is no schema, no migrations, no query functions in the open repository. Searching for schema.ts finds only an unrelated toy example app.

The giveaway is a helper called isEntityNotFound that inspects 404 response shapes to tell "row missing" apart from "route not deployed". The open-source client is guessing at its own backend's contract by status code. A rebuilder gets the wire protocol and must invent the entire data model.

copy thisserver/app.ts:91-602

One app factory, three deployments

createHonoApp() is the single entry point for the local web server, the Electron-embedded server and the Docker image. The differences are environment variables: ELECTRON_APP, IS_PACKAGED, NODE_ENV. No forked server, no duplicated route table.

This is the highest-value structural idea in the codebase and it is free to copy. It is also why the earlier Next.js build failed: they migrated to Vite + Hono explicitly because Next.js dragged 241 MB of dependencies into a package meant to be run with npx. The maintainer's public post-mortem is refreshingly blunt about it.

"It made no sense to do it in hindsight. We chose Next initially because that's just what we were used to using to build web apps. The lesson here is that your stack matters a lot, depending on the use case."

What happens when you click "Run" on a tool

Twelve hops. Worth reading closely, because the shape of hops 4, 6 and 7 is the shape of the whole product.

Form generated from JSON Schema client/src/components/ToolsTab.tsx → generateFormFieldsFromSchema The tool's inputSchema becomes a form. No hand-written UI per tool.
Click Run client/src/lib/mcp-tools-api.ts:47 executeToolApi(serverName, tool, params).
POST to the local server POST /api/mcp/tools/execute Body: { serverId, toolName, parameters }. Plain HTTP; the browser never speaks MCP itself.
One execution at a time — else 409 server/routes/mcp/tools.ts:142-236 The route builds an ExecutionContext and refuses a second concurrent execution with 409 Conflict. This is a deliberate trade: a single in-flight call makes multi-round elicitation tractable as a race between the execution promise and the next elicitation, instead of concurrent bookkeeping.

Both publish to the bus.
Fan-out to the UI, two different ways GET /api/mcp/servers/rpc/stream (SSE) · data-rpc-log parts (hosted) Locally it is Server-Sent Events with buffer replay and a 15-second keepalive. In hosted mode it piggybacks on the AI SDK chat data stream as custom data-rpc-log parts. Two transports for the same events.
If the tool asks a question 202 { status: "elicitation_required", requestId, request } The route races the execution against the next enqueued elicitation and returns 202 so the UI can render a form. Timeout is 300,000 ms on the chat path.
Result returns 200 { status: "completed", result } Front end stores result and structuredContent, then validates against the declared outputSchema.
Widget detection, in priority order _meta.ui.resourceUri → openai/outputTemplate → inline ui:// resource MCP Apps, then ChatGPT Apps, then MCP-UI. First match wins.

Render, next to the log entry from hop 6 ResultsPanel / ToolPart + JsonRpcLoggerView The whole point: the human sees the rendered result and the raw wire traffic that produced it, side by side.

The one architectural idea to steal

The browser never speaks MCP. A local Node process owns every connection, and the UI is a thin HTTP client over it. That is what makes stdio inspection possible at all — a browser cannot spawn a subprocess — and it is why the same code serves a web app, a desktop app and a CLI. Everything else in this teardown is detail; this is the decision.

05 — The debugger

Eighteen screens, and five features nobody else has

Most of the surface is table stakes. Five parts are genuinely differentiated, and they are the ones a competitor has to match.

The differentiated five

1sdk/src/server-doctor.ts · http-server-doctor.ts

Server Doctor — eight sequenced checks

Stateless HTTP probe → full client connect → capture initInfo → capture capabilities → list tools → list resources → list resource templates → list prompts. Rolls up to ready / oauth_required / partial / error, and short-circuits to oauth_required before connecting if credentials are missing — so a failing probe tells the user "log in first", not "your server is down". Shipped twice: a Node version and a browser-safe version using the transports directly.

2sdk/src/error-describer/catalog.ts:162

Error describer — 34 catalogued failures

Each entry carries a title, a one-liner, likely causes, next steps, a docs anchor, a severity, and an origin: user_server / user_config / mcpjam / ambiguous. The comment is explicit that origin means "who has to act", not blame — it routes a failure to the right person. A credentialOwner flag re-labels auth errors as MCPJam's problem when MCPJam holds the token. Covers JSON-RPC codes, transport errno codes, OAuth failures, provider quota errors, and its own sentinel errors matched by class-name regex because class identity is lost across JS realms.

3sdk/src/server-snapshot.ts · server-diff.ts

Snapshot and diff — regression detection in CI

Capture a server's full surface, diff two captures, classify every field change as breaking / non_breaking / informational, roll up per entity by max severity, and gate CI on failOn: breaking | any | none. Schema changes go through a narrowing-versus-widening comparison rather than a raw diff. Run it either side of a deploy.

4docs/inspector/guided-oauth.mdx · sdk/src/oauth-proxy.ts

Guided OAuth debugger

Steps the five phases — discovery, client registration, PKCE, authorization redirect, token exchange — showing the HTTP request and response for each, against four OAuth spec versions. Captures the exact resource value sent, validates iss per RFC 9207 where the version requires it, redacts tokens, and persists the trace across reloads. The backend fetcher DNS-pins the resolved IP, refuses loopback and private hosts, forces HTTPS, uses manual redirect mode and bounds body reads. That is a properly paranoid SSRF story.

5sdk/src/host-compat/catalog.generated.ts

Host compatibility catalogue

Connect-time capability probes for sixteen real hosts, recorded with dates and provenance, plus a full-capability reference profile to diff against. This is the only place a public dataset of "what Cursor 3.4.20 actually declares" exists. It is also the asset that took the longest to build and would take a competitor longest to reproduce, because it requires physically probing every host on every release.

gapsdk/src/server-diff.ts:232-237

The diff misses the attack it was built for

A tool description change is classified informational. Removing a tool is breaking; rewriting what a tool claims to do is not. But rewriting the description is the classic MCP rug pull — the tool's behaviour and intent change while its schema stays identical. A CI gate on failOn: breaking will wave it straight through. This is a two-line fix with real security value, and the highest-leverage thing a competitor could get right on day one.

How the log bus actually works

This is the core of any MCP debugger, so the mechanism matters more than the feature list.

Event identity

Every event gets rpc:<processNonce>:<counter>, minted once per physical event — never per JSON-RPC id or method. So replays are idempotent on the client, but a retry and its original still occupy separate rows. Correct, and easy to get wrong.

Listener isolation

Subscriber exceptions are caught and logged, because "an unguarded listener would propagate into the PRODUCER" — a broken UI panel must never fail the MCP call it is observing. Worth stealing verbatim.

Bounds

500 events per server, enforced by splice on write. Count-based only — there is no byte cap, so 500 large tool results is 500 large tool results in RAM.

Progress is separate

A different store keyed serverId → progressToken → latest. Last-write-wins per token, not a log. Auto-expires after 5 minutes on a 60-second sweep.

Nothing survives restart

Both buses are pure in-memory EventEmitters. Restart the server and every captured frame is gone. For a debugger, that is a real product limitation, not just an implementation note.

No session export

Searched for HAR-style capture: nothing. You can download the log buffer and you get per-flow OAuth HTTP history, but there is no "export this whole debugging session and send it to a colleague".

trustsdk/src/mcp-client-manager/MCPClientManager.ts:2576

The server under test is not sandboxed

sandbox-policy.ts is thorough — but it sandboxes rendered widget content, resolving CSP directives and iframe permissions with a documented precedence and a hosted-mode hard clamp that strips wildcards and private-network targets regardless of what a profile asks for. Good work, wrong target.

The stdio MCP server itself is spawned with a plain StdioClientTransport. No container, no seccomp, no user drop, no CPU or memory limit. A search for cgroup, rlimit, resourceLimits finds nothing. The only real process isolation in the product is the E2B cloud VM, and that is for MCPJam's own agent feature, not a safety wrapper around your code.

trustsdk/src/telemetry.ts · EvalTest.ts:310-317

The debugger phones home by default

Redaction is genuinely careful: Authorization and Cookie headers, bearer tokens, access/refresh/id tokens, client_secret, code_verifier and PKCE codes are stripped both by key name and by regex over free text. Conformance reports go further and drop whole containers — httpAttempts, http, logs, credentials, headers — because an OAuth conformance run's raw evidence contains live tokens. A client-side ratchet test freezes the list of files allowed to call posthog.capture directly.

But it is opt-out, not opt-in: DO_NOT_TRACK=1 or MCPJAM_TELEMETRY_DISABLED=1. And every local EvalTest.run() fires an eval_test_run_triggered event with iteration and concurrency counts to a hardcoded PostHog key — not mentioned in any eval documentation. Sentry crash reporting is on by default with a DSN hardcoded in source.

Every local secret is plaintext behind a file mode

CLI access and refresh tokens are written to ~/.config/mcpjam/auth.json in the clear, protected only by chmod 0600. No OS keychain. Any process running as the same user reads them, and so does any backup or sync tool that ignores POSIX modes. Server-side dev secrets follow the same pattern in ~/.mcpjam/ — though correctly gated to development, with production forced to supply them by environment variable.

Worse in the browser: legacy per-server OAuth entries stored client_secret in localStorage, readable by any XSS or extension. Encryption is referenced only in comments — "a decrypted access token", rotateStoredCredential — meaning it happens server-side in the closed repository. A search for encrypt, cipher or keytar in the open server code finds nothing.

secretsserver/services/internal-backend.ts:17-21

One token to impersonate every tenant

INSPECTOR_SERVICE_TOKEN is a single shared credential gating all internal backend calls. Anyone holding it can act as the inspector for every organisation. There is no per-instance identity, no rotation visible in the open code.

designservices/tunnel-manager.ts:26-29

Tunnel auth is a secret in a URL

The public tunnel URL carries ?k=<secret>. Holding the URL is holding the credential. The comment is candid — "Full bearer URL (contains the ?k= secret). Held in memory ONLY" — and the mitigations are short-lived possession plus backend revocation. Close codes are properly split into permanent (bad token, revoked, replaced) versus transient (edge restart, network drop with 1–30 s jittered backoff), and the socket does 64 KB chunking with a 1 MB backpressure watermark and a 25-second heartbeat. The plumbing is good; the auth model is a URL secret.

Multi-tenancy

Hierarchy: Organisation → Project → Environment (revisioned) → Run, with a Host config pinned per environment. Launches pin an immutable (environmentId, revision) plus the host's config id at resolve time, so a host rotating underneath an unchanged revision is reported as detectable drift rather than silently executed. That is a genuinely good idea for reproducible evals.

Connection requests are isolated per row with lease-based single-worker ownership — a 409 means someone else holds the lease. Guest sessions get a real user row and the same authorisation model: "There is no guest branch." Organisation membership syncs to WorkOS on independent, individually-failable timelines, so API-key minting checks a live readiness endpoint rather than trusting session state.

But the enforcement is invisible. Row-level access control lives in Convex functions that are not published. The open code only assumes membership gates access.

Migrations

What exists is client-side and pragmatic: the CLI auth file carries a version and rejects mismatches outright; the browser ships a one-time, resumable localStorage-to-Convex migration gated by a flag, tracking per-project progress so a partial failure retries without duplicating rows; the progress record itself was upgraded in place from a bare string array to a keyed object.

Cross-version tolerance is by optional field, not negotiation — newer backend fields are optional on the client "so an older backend still parses". There are no server schema migrations in the repository, because there is no server schema in the repository.

07 — The evals engine

Deterministic predicates gate; the LLM judge only advises

This is the most commercially important part of MCPJam and the best-designed idea in it: code-checkable assertions decide pass or fail, and the language model's opinion is a separate, advisory number. Most eval products get this backwards.

The object model

Suite
Cases plus shared defaults: servers, models, checks, judge config, argument-matching mode.
Case / EvalTest
One scenario: prompt turns, expected tools, checks.
Run
One execution of a suite → N iterations, case × model.
Iteration
One execution with a transcript, tool calls, token counts, verdict.
Predicate
A pure function over the transcript. Deterministic. This is the gate.
Matcher
Separate tool-call comparator producing missing / extra / out-of-order / argument-mismatch.
Judge
LLM "goal completion" score. Advisory unless you opt in.
Verdict
predicates AND tool-match AND (unless disabled) no tool errors.

A predicate that cannot be evaluated fails. It never passes by default. responseMatches carries a ReDoS guard against nested quantifiers.

Authoring

Two surfaces over one shape. Code-first is plain Vitest or Jest — no bespoke config format, discovery is a standard glob:

test("list-workspaces accuracy > 80%", async () => {
  const t = new EvalTest({
    name: "list-workspaces",
    test: async (runner: HostRunner) => {
      const r = await runner.run("Show me all my workspaces");
      return r.hasToolCall("asana_list_workspaces");
    },
  });
  await t.run(testAgent, {
    iterations: 5, retries: 1, timeoutMs: 60000,
    onFailure: (report) => console.log(report),
  });
  expect(t.accuracy()).toBeGreaterThan(0.8);
});

The hosted surface authors the same cases as JSON through the CLI or the UI, in four parts: scenario, prompt turns, expected tools, expected output. SDK-reported runs get a "CI" chip in the UI, and the metric label flips between "Pass Rate" and "Accuracy" depending on origin.

13 predicate types

toolCalledWith, toolCalledAtLeastOnce, toolNeverCalled, firstToolWas, responseContains, responseMatches, noToolErrors, finalAssistantMessageNonEmpty, tokenBudgetUnder, widgetRendered, widgetRenderLatencyUnder, widgetNoConsoleErrors, turnCountUnder.

The docs say twelve. The code has thirteen — turnCountUnder is undocumented.

9 tool-call validators

Default model openai/gpt-5.4-mini, default threshold 0.7, scale 0.0–1.0 plus a one-line reason and rubric hits. Capped at 0.85 when there is no expectedOutput to grade against — a self-acknowledged weak baseline. The grading prompt itself is a Convex mutation in the closed repository, so its calibration cannot be audited.

CIdocs/cli/ci.mdx:418-423

The CI gate is not built in

mcpjam eval run and eval status exit non-zero only on transport or API errors — not on eval failure. The documented workflow ends with the user's own shell assertion: [ "$(jq -r '.run.result' …)" = "passed" ]. There is a passCriteria.minimumPassRate field, but wiring it to the exit code is left to you.

Conformance is better served here: it emits JUnit XML natively through a config-driven matrix runner. Evals have no native JUnit path at all.

Where the evals engine is weak

reproducibility

There is no seed

No seed parameter exists anywhere in EvalTest or HostRunner. The documented answer is "use low temperature" and average over thirty-plus iterations. You can never get a byte-identical reproduction of one specific failure — which is exactly what you want when debugging a flaky tool call. This is the single largest functional gap in the product and an obvious place to beat it.

regression

No datasets, no baselines

There is no golden-dataset primitive and no baseline pinning. The closest features are a manual two-run Compare view and a per-case "pass rate across runs" column. Nothing automatically alerts on regression, and nothing feeds a historical baseline into the CI gate. For a product whose pitch is "catch it before you ship", that is a conspicuous hole.

testing

The riskiest file is the least tested

evals-runner.ts is 3,781 lines mixing trace building, timeout orchestration, attachment seeding and iteration streaming — and has no colocated test file. Its neighbours (recorder.ts, step-handlers.ts) are covered. The SDK layer is fine: 215 test files, 15 eval-specific, plus predicate tests and a JSON parity fixture.

cost

Estimates, not caps

Hosted runs consume organisation credits per iteration, with a pre-run estimate and no hard ceiling. Combine that with unbounded server-side concurrency and a suite times a model matrix, and a mistyped iteration count is a billing event. Failure classification is at least narrowly anchored to two markers so a transient server error that merely mentions "quota" cannot pause a schedule.

08 — Conformance

The scoring model is the best thing in the repository

Conformance and evals answer different questions. Conformance asks "does this obey the specification" — stateless, no model involved. Evals ask "can a model use this well" — stochastic, judged over many runs. Four suites, one number, and a genuinely principled way of producing it.

Four suites

mcp-conformance
Protocol compliance. 50 checks — server-initialize, ping, tools-x-mcp-header-declarations-valid, and so on.
oauth-conformance
The authorization stack, across four spec versions.
apps-conformance
MCP Apps and ChatGPT Apps widget contracts, including SEP-1865 visibility validation.
tasks-conformance
The Tasks extension.

conformance-catalog.ts is a deliberately dependency-free mirror of every check's title and description across three suites, so a UI can preview "what will run" without importing Node-only transport code. A dedicated parity test catches drift from the canonical source. That is a small, disciplined piece of engineering.

The 0–100 score, and why it is right

steal thissdk/src/conformance-score.ts:31-72

MUSTs own 95 of the 100 points. Advice — SHOULDs and MAYs — owns the remaining 5, deducted at 2 and 1 points, and capped so advice can never fail a MUST-clean server. The doctrine of the specification is encoded in the arithmetic.

Not-applicable checks leave the denominator entirely. HTTP checks against a stdio server are free, not failures.

Could-not-run checks stay in the denominator as unearned points. So an incomplete run can never show 100 — you cannot game the score by breaking the harness.

The score is null when nothing was applicable. It refuses to invent a number for a vacuous run.

100 means exactly: every applicable check ran, passed, and nothing was advised.

One caveat on the shareable score

Results are published at results/:runToken and, per the router's own comment, are "deliberately readable with no session at all — the link IS the credential." That is why conformance redaction drops whole containers rather than scrubbing fields: an OAuth conformance run's raw HTTP evidence contains live access and refresh tokens. The redaction is correct because the sharing model is loose. If you copy the sharing model, copy the redaction with it.

The pipeline

Changesets-based, baseBranch: main, access: public. Six internal packages are excluded from versioning. release.yml is workflow_dispatch only — a human picks a scope (packages-only, inspector-only, or full), the job checks changeset status, gates the scope against pending changesets, versions, builds, injects Sentry source maps, publishes, then optionally triggers the macOS and Windows desktop builds by workflow_call and a Railway production deploy plus a backend deploy dispatch.

Three packages — @mcpjam/sdk, @mcpjam/cli, @mcpjam/inspector — carry identical time.modified timestamps to the minute, confirming a single lockstep publish per run.

Contributors are never told about changesets

CONTRIBUTING.md contains zero mentions of "changeset". Versioning is maintainer-driven after merge — consistent with one author writing 58% of commits in the visible window, and an AI coding bot being the second-largest contributor by volume. That is not a fatal flaw, but it tells you where the institutional knowledge lives, and that outside contributions do not carry their own release metadata.

GitHub PR checks: the most ambitious feature in the repository

A separate worker subsystem from the eval CLI. It claims jobs from the backend, then has to work out how to build and start an arbitrary repository's MCP server before it can test anything. It does that with a three-rung ladder:

1. Operator override

A recipe table keyed by repository. Deliberately kept empty in production — the escape hatch exists but is not used, which is the right discipline.

2. Declared config

An mcpjam.yaml in the target repository. The path they want people on.

3. Agentic detection

An agent reads the repository and figures out the build and start commands. 1,947 lines in the detector alone.

check-plan.ts models attempt phases, failure kinds and actions as an explicit state machine with a PlanUnreachableError — so "we could not work out how to start your server" is a distinct, reportable outcome rather than a generic failure. The whole path is 1,690 lines of sandbox plus 1,473 of worker plus 763 of resolve-and-start. It is the hardest thing in the product and the least likely to be reproduced.

criticalissues #2406 · #1891 · #2362CVE-2026-23744

The trust boundary is "not being reachable", and Docker breaks it

This tool spawns arbitrary user-supplied commands. That is the product, not a bug — and a code comment in the local-machine executor says so plainly: "This is NOT a sandbox. Commands run as the OS user with all of that user's permissions… it is NOT a security boundary." Honest, and correct as a design statement.

The problem is what protects that capability. Not authentication — network binding. Two reporters filed [SECURITY] issues, both say they disclosed privately first and went public after being ignored, and both are still open:

#2406
Unauthenticated MCP manager and adapter HTTP endpoints → remote code execution if the connected server can run commands. Advisory GHSA-2v3v-5588-2h53, disclosed 12 Feb 2026.
#1891
The session-token endpoint's Host-header allowlist can be spoofed to mint a valid session token, which then unlocks /api/mcp/connect. Reported 20 Feb 2026.
#2362
Live proof of concept for the related advisory GHSA-232v-j27c-5pp6 (CVE-2026-23744): curl the connect endpoint with {"command":"/bin/sh","args":["-c","sleep 10"]} and time the response.

Current state, verified in the code: the native default bind is now 127.0.0.1, and a comment tells Docker users to publish as -p 127.0.0.1:6274:6274. Desktop and npx installs are protected. Docker still binds 0.0.0.0, because port forwarding requires it — so anyone following an older docker run -p 6274:6274 example is exposed exactly as the proof of concept describes. No application-layer authentication was added to /api/mcp/connect itself. The fix is a network default, not an authorisation check.

Secondary finding in the same area: the global CORS policy uses a configured allowlist, but seven individual SSE and stream routes override it with a hardcoded wildcard — in servers.ts, subscribe.ts, subscriptions.ts, mrtr.ts, widget-files.ts and two XAA metadata routes. Whether each leaks depends on that stream's payload, but ad-hoc wildcards sitting next to a stricter global default is a maintenance hazard on its own.

SECURITY.md is one line: email founders@mcpjam.com. No PGP key, no scope, no response-time commitment, no bounty. For a tool whose core capability is arbitrary command execution, that is the wrong level of investment.

Hand-mirrored contracts

The tunnel WebSocket frame and close-code protocol is "HAND-MIRRORED" across three repositories — inspector, backend, CLI — with no shared package. The Convex record shapes are similarly mirrored by hand into TypeScript interfaces. Every one of those is a silent-drift waiting to happen.

Naming collision

routes/relay.ts is a PostHog analytics proxy, mounted at /relay to defeat ad blockers. The actual MCP tunnel machinery is relay-client.ts and tunnel-manager.ts. Anyone grepping "relay" to understand tunnelling lands on the wrong file first. I nearly did.

Swallowed errors

39 empty catch {} blocks in server code. Many are documented as intentionally ignoring close errors, but the pattern is repeated ad hoc rather than expressed once as a helper — so you cannot tell deliberate from accidental without reading each one.

11 — If you are building this

What to copy, what to skip, what to beat

The honest read: matching MCPJam feature-for-feature is a multi-year project for a team. Beating it on the four gaps below is a quarter for two people. Pick the second one.

Copy outright

  • Local Node process owns all connections; the UI is a thin HTTP client. Non-negotiable — it is what makes stdio inspection possible.
  • One app factory for every deployment, switched by environment variable.
  • Log bus with per-physical-event ids and caught listener exceptions, so a broken panel cannot fail an MCP call.
  • The conformance scoring model: MUSTs own 95 points, not-applicable leaves the denominator, could-not-run stays unearned, null for vacuous runs.
  • Predicates gate, judge advises. A predicate that cannot be evaluated fails.
  • Error catalogue with an origin field that routes a failure to whoever must act.
  • Grep-based CI guards for platform-safety invariants, run on source and on dist.
  • Streamable HTTP first, automatic SSE fallback. Never make the user choose.

Skip, at least at first

  • The tunnel relay. Three hand-mirrored protocol copies and URL-secret auth, to solve a problem ngrok already solves.
  • The XAA / ID-JAG bench. 2,655 route lines for a draft standard almost nobody deploys yet.
  • The widget renderer. Double and triple iframe nesting, a window.openai shim, Playwright at runtime, and two separate sandbox type systems. Enormous surface for one narrow audience.
  • The E2B "Computer". A different product wearing the same badge.
  • Slack and Discord surfaces. Distribution, not debugging.
  • Agentic build detection for PR checks. Require a config file instead. Ship rung 2 of their ladder and skip rung 3.
  • Tasks support. MCPJam itself removed it for "lack of adoption and a complete rework coming in the new spec". One host declares it.

Beat them here

  • Determinism. Record and replay every LLM and tool interaction, keyed by a seed. There is no seed anywhere in their engine. This is the biggest single gap.
  • Durable debug history. Their RPC log dies with the process, capped at 500 events with no byte limit and no session export. Persist it, index it, make it shareable as a file.
  • Regression baselines. Pin a golden run, diff every subsequent run against it, fail CI natively with a non-zero exit code. They make you write the shell assertion yourself.
  • Rug-pull detection that works. Classify tool-description changes as breaking, or at minimum surface them behind their own flag. Theirs are informational.
  • Sandbox the server under test. Container or seccomp, with CPU and memory limits. They have none, and it is the recurring theme of every security report against them.
  • Real authentication on the local API. Not a bind address.

A build order that gets to useful in four phases

01

The proxy and the log — about two weeks

Node process, official MCP client SDK, three transports with automatic fallback, spawn stdio children and drain stderr. Tee every frame to a log bus with per-event ids. Stream to a browser over SSE. Write it to disk from day one — that is your first differentiator and it costs nothing to add early. Add real bearer auth on the local API immediately; do not inherit their bind-address-as-security model.

The strategic read

MCPJam's moat is not its code. It is the host compatibility catalogue — connect-time probes of sixteen real hosts, re-run every release — and the near-daily release cadence that keeps it current against a specification that just deleted its own handshake. Those are operational assets, not architectural ones, and they are expensive precisely because they are boring.

Its weakness is that everything durable, everything monetised, and everything auditable sits outside the open repository, behind either a Convex deployment you cannot see or an Enterprise Edition licence you must pay for. Combine that with two unfixed public RCE reports, a one-line security policy, and 58% of commits from a single author, and the risk of building on MCPJam is materially higher than the risk of building beside it.

Method

The MCPJam/inspector repository was cloned and read directly on 14 August 2026, with file and line references retained for every claim. Line counts, file sizes, any-cast counts, test-file ratios and commit statistics were produced by commands run against that clone, not estimated. Issue counts, release dates and star counts come from the GitHub API; download figures from the npm registry; both on the same date.

The clone is shallow — 201 commits covering 5 to 14 August 2026 — so commit-velocity and contributor figures describe that ten-day window, not the project's life; releases trace back at least to June 2026. And the Convex backend, the LLM judge prompt, the token-encryption layer and the tenant-isolation rules are in a repository that is not published, so statements about them are inferences from the client-side contracts that call them, and are labelled as such throughout.

Community quotations are from public Reddit threads, attributed inline. Security findings reference the reporters' own public issue text; where the current code contradicts a report, both are stated.
